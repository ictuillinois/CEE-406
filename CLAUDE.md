# CEE 406 Pavement Design I — Project Guide

## Overview

Astro 6 static course portal for CEE 406 (UIUC, Prof. Imad L. Al-Qadi). Content is organized **by homework**: 10 homework pages, a 20-part online textbook (Huang 2004), and interactive React tools. Design system inherited from `ictuillinois/ict-mechanics` (navy `#0F1A2E` / orange `#E87722`, Sora + IBM Plex, dark mode, Pagefind search).

## Getting started

```bash
npm install
npm run dev      # localhost:4321
npm run build    # astro build + pagefind indexing
```

Requires Node >= 22.12.0.

## Architecture rules

- **Content lives in `src/data/homeworks.ts` (metadata, problems, downloads), `src/data/hwGuides.ts` (purpose, KaTeX concept cards, steps, pitfalls), `src/data/textbook.ts`, and `src/data/tools.ts` (the tool catalog: name, slug, color, HW chips, reference, description, SVG glyph)** — pages under `src/pages/homeworks/[id].astro` and `src/pages/textbook/[id].astro` are generated from them. To change homework content, edit the data files, not the pages. Guide bodies are HTML with KaTeX (`$...$`/`$$...$$`, backslashes escaped in TS strings).
- React tools are islands mounted with `client:only="react"` (Plotly is browser-only; do not SSR them). Each tool: `src/components/react/<tool>/App.tsx` + shared `src/components/react/tools.css` + a wrapper page in `src/pages/tools/<tool>/index.astro`, registered in `src/data/tools.ts`, which the tools index AND the landing page both render from. Never add a tool to only one of those surfaces — they used to keep separate arrays and the landing page silently drifted to advertising 2 tools while 18 were live. **A released tool must also ship its miniature** — `image` + `imageAlt` in `tools.ts` and the file under `public/tools/` — because both surfaces fall back to the 120×44 stroke glyph without one, and a glyph in a row of real screenshots reads as the unfinished card; `lea` shipped that way and looked half-built beside the other three. House style, so the set reads as one: the tool at **1312×788 in light mode**, nav bar at the top, its own control panel down the left, its principal output filling the rest — the frame a student sees a few seconds after opening it — encoded with `sharp` at webp quality ~80. The cards crop to 16:9, so nothing essential goes in the top or bottom eighth. `release.test.mjs` fails both ways: a released tool without a shot, and a locked tool with one. **The ORDER of the `tools` array is the order a student sees** — both surfaces filter it by the release gate and render what survives in place — so the released tools lead it in the order the course wants them shown (cross-section-studio, gear3d, contact-stress, lea) and everything still locked follows in homework order. Releasing a tool is therefore also a decision about where in that lead it goes. Twenty-one tools are live: mr-fitter + cbr (HW2), mastercurve (HW2/8, Ch. 7 + App. A), lea + stress-explorer (HW3/4), esal-calculator + eswl (HW5/7), drainage (HW6), aashto (HW7/9), damage (HW8), pca + westergaard + joints (HW9), acr + lca (HW10), psi (HW1/10, Ch. 9), backcalc (Ch. 9/13), reliability (Ch. 10), cross-section-studio (figures, Ch. 1), gear3d (HW4/5, Ch. 6), contact-stress (HW3/4, Ch. 1).
- **`cross-section-studio` and `gear3d` are the two islands that are not React apps.** Both are ports of standalone Three.js E-Labs from `Johann-Cardenas.github.io/e-labs/`, and both follow one shape: the engine is a single `init*(root)` closure that owns the DOM imperatively and returns a disposer, and the `*App.tsx` supplies markup and calls it from one effect. Keep them apart — React must never be asked to re-render a WebGL scene, and the disposer must keep tearing down the rAF loop, the ResizeObserver, the WebGL context and the document `keydown` handlers or a remount leaves two render loops on one canvas. Both opt out of the `.cee-tool` two-column grid (via `.cee-tool.xs-tool` / `.cee-tool.g3-tool`) while keeping its tokens, and both carry control help on `title` rather than `<Tip>`, because their side rails are `overflow: auto` and would clip an absolutely positioned popover. `three` is pinned to `0.160.1` — the version both upstream import maps pin — so the render is bit-for-bit the same.
- **The two E-Lab ports are maintained by re-running their transform scripts, not by hand-editing.** `gear3d/engine/**` is a byte-for-byte copy of the upstream `src/**` (36 modules; the only hand edit is a PORT NOTE in `io/exportRaster.js`, where a token lookup had to move off `documentElement`), and `gear3d.js` / `gear3d.css` are generated from upstream `main.js` / `styles.css` by scripts that assert every anchor they rewrite and fail loudly if one has moved. The body of `gear3d.js` is deliberately **not** re-indented into its closure, so `diff` against upstream reports the twenty-odd real changes rather than three thousand whitespace ones. If you change one of these files by hand, the next upstream sync silently loses it — put the change in the transform instead.
- **`cross-section-studio` works in SI or English, and the switch is a SOFT conversion.** Every length in its state is millimeters, always, and the renderer sees nothing else. The toolbar toggle is a presentation layer over that plus one thing it would be dishonest to leave out: it re-rounds. A pavement thickness is a DESIGNATION, not a measurement, and FAA P-401 is specified as "75 mm (3 in.)" because those are the same lift, so English does not relabel a 75-mm layer as 2.95 in, it makes it a 3-in layer. **Two constants do two jobs and crossing them is silent**: `NOMINAL_MM_PER_IN` (25) rounds a designation and only the switch touches it; `MM_PER_IN` (25.4) draws one, so what is stored for 3 in is 3 x 25.4 and the figure is exactly as tall as its own label. The map is deliberately **not idempotent** (applying metric to English twice inflates by 1.6% a pass), which is why `convertLengths` runs only on a real switch and takes a `'layers'` scope for the case where a template has just dropped metric numbers into a section already in inches. Three FAA designations are not multiples of 25 (280, 330, 510) so a round trip returns them as 275, 325 and 500, once and then stable. All of it lives in `units.ts`, which imports nothing, and `units.test.mjs` pins the table, the round trips, the non-idempotence and the field limits against every thickness the studio ships. The unit choice persists in `localStorage('cee406-xs-units')` and rides in the project file, the undo snapshot and a reset.
- **`gear3d` works in SI or English too, and where the studio re-designates, gear3d ROUNDS.** Storage is canonical (mm / kg / kN / kPa / mm²) and `engine/core/units.js` already switched all five families at once, so the figure, the dimension engine and the scale bar were always unit-aware. Two things were not. (1) Five readouts printed millimeters whatever the toolbar said — the hover coordinates, the contact-patch tooltip, both structure-tree tags, three lines of the wide-base report — plus the title block's Units cell, and the switch never re-lit itself, so a restored session came back in inches showing SI. (2) English was printed as if it were exact: a 1854 mm track read **72.99 in**, a hundredth of an inch the data does not have and harder to read than 73. **`engine/core/readable.js` is the answer to the second**: it wraps the five `format*` functions and rounds English to **three significant figures** (lengths floored at one whole inch, because only lengths reach four digits — a 75-ft double is 1124 in and three figures alone would say 1120). Wrapping rather than editing thirty call sites is deliberate: a rule remembered thirty times gets missed once. **Three figures is a measured number, not a taste**: it is what recovers the SOURCE's own magnitude wherever the citation was itself converted from English, which here is most of it (4572 mm → 180 in, 1372 mm → 54 in, 279 mm → 11 in, 1054 mm → 41.5 in, 44.5 kN → 10 kip, 13,608 kg → 30,000 lb), and over every length, load and weight the library cites the worst distortion is **0.41%**. Where the citation really is metric the reading stays honest rather than tidy (300 mm is 11.8 in, not the data book's nominal 12) — recovering that would mean trusting the designation, and the 9.00 in a 9.00R20 is a series number, not a section width.
- **Three things in gear3d must NOT follow the switch, and one list must.** Not: **the annotation engine**, which imports `units.js` directly, so a figure's dimension labels stay the reader's own Precision setting — that is why the structure tree can read 51.6 in beside a dimension line reading 52 in, and why a panel must never take `precision` from the reader (two panels disagreeing would have no explanation on screen; a panel and the figure have a Precision control). Not: **the data exports** (`footprint.csv`, the Abaqus deck, OBJ/glTF — always millimeters, each saying so in its own header). Not: **`<input type="number">` values**, which go through `plainLength` because `formatNumber` groups thousands with U+202F and a separator silently blanks that field. Must: **`setUnitSystem()`'s refresh list** — every function that formats through `UNIT_SYSTEMS` is on it or is exempt with a stated reason. `renderTree` joined it when its tags stopped being hardcoded, and `renderWideBaseReport` exists only for this: the wide-base report is a RECORD of one swap and must not be recomputed, so it used to be written into the DOM at click time and could not be re-printed either. The choice rides the session autosave and the project file, and **the file's units win on open**, because a `.gear3d` is a drawing sheet that records the system it was drawn in; that is why there is deliberately no `localStorage` preference here to fight it.
- **All of that lives UPSTREAM, and `port-main.mjs` is 22 rewrites of pure port adaptation again.** It was first written as an eleventh transform section, which was wrong: these are defects and a feature the standalone E-Lab wants too, and a transform that carries product changes stops being a transform and becomes a fork. They were moved into `Johann-Cardenas.github.io/e-labs/gear3d` (main.js, index.html, the new `src/core/readable.js`, and §15 of its own suite, which took it from 176 to 187 checks) and came back through a re-sync. The sync also brought the transform's anchors from British to American, because upstream respelled itself in `11f9c56` and an anchor's spelling tracks upstream, never this repository. Regenerating from today's upstream reproduces the shipped `gear3d.js` exactly, which is the cheapest check that the pipeline is still faithful.
- **A port's data and textures live in `public/`, not beside its modules.** Upstream Gear3D resolves its vehicle library with `new URL('./src/data/', import.meta.url)`; under Vite that module is bundled into `_astro/` and the data is no longer beside it. The library and the CC0 textures are served from `public/gear3d/` and addressed through `BASE_URL`. `TextureLibrary` and `AssetLibrary` already take an injectable `basePath`, so nothing in the engine had to change for it.
- **`--g3-fig-*` and the figure ink in `gear3d.js` are deliberately not themed.** They are the colors of the *drawing*, and they end up in PNGs, SVGs and PDFs that go into student reports. A figure must not change because the course site changed its accent color. The app chrome around them is re-skinned to the course palette; the plate is not.
- **A re-skin does not inherit the upstream's contrast results — re-run the gate.** `gear3d/tokens.test.mjs` is a port of §14 of the upstream E-Lab's own suite, and it caught a real regression the re-skin introduced: upstream's dark `--g3-muted` is documented as "4.53:1 at worst", but that was measured on upstream's slate; the course's raised navy `#1b2740` is lighter, and the same token landed at **4.46:1** — an AA failure on every secondary label in the dark theme, caused purely by moving the surface underneath it. It is lifted to `#8293a1` (4.71:1) in `port-css.mjs`. Run it with `node --test src/components/react/gear3d/tokens.test.mjs`.
- **`gear3d`'s meshes are gated by `geometry.test.mjs`, and nothing else in the repo builds one.** `render.test.mjs` server-renders every island, but a `client:only` island's effects never run under `renderToString`, so it never reaches a line of three.js; the upstream E-Lab's 176 checks cover the data, the layout and the exports and never touch geometry either. The gap is real and was expensive: a `mergeGeometries` call that threw on its first invocation passed both suites and rendered an empty viewport. The new gate builds the tire, rim and hub for **every designation the shipped library mounts**, at every quality and both handednesses, and asserts the invariants that a rendered figure depends on — the tire is exactly as wide as its published section width (uniform Catmull-Rom overshot it by 0.6–1.1 mm on every tire), no meridian crease exceeds 12° (it reached 31°, and that is the terraced band that made a sidewall read as a stack of washers), the tire never intersects the rim, the lug nuts stand outboard of the disc face (they were buried 24–74 mm inside it, on every wheel, always), the hub boss closes the bore it exists to close (it was 0.28 against a 0.30 bore), and 34 tires at draft stay under 1.2 M triangles. It needs no GPU and no canvas — the tire, rim and hub builders touch no DOM, only the texture builders do, and that is worth preserving. Run it with `node --test`, not `--experimental-strip-types`.
- **One wheel, one table of stations.** `wheelStations()` in `rim.js` is the only answer to where any part of a wheel sits, and `hub.js` and `tire.js` both read it. Three separate defects were one defect: two modules deriving the same axial station from different parameters, a boss sized independently of the bore it plugs, and a bead placed at a number that has nothing to do with where a bead seats. Passing the same `offsetRatio` to both builders would have fixed the day's bug and none of the next ones. **Do not reintroduce a wheel dimension that is computed in two places.**
- **`contact-stress` is the one tool whose physics is a trained network, and the network is not in this repo.** phyContactGAN (Lang, Villamil & Al-Qadi 2026, ICT — three 135 MB checkpoints plus 6 GB of training arrays) lives only in the gitignored Box archive `Contact Stress Predictor/`, beside the offline pipeline that reads it. What ships is `public/tools/contact-stress/` — a precomputed sample of the model's **output** over the whole of its training domain, compressed to a shared PCA basis per tire and channel (DTA 6,300 grid nodes, K = 64/32/28 at 2 mm, 2.8 MB gzip; WBT 119 nodes, K = 26/18/18, 1.0 MB, lazy-loaded). `predictor.ts` decodes it and reconstructs `mean + Σ c_k φ_k` with 4-point cubic interpolation on the axes; measured held-out error against the generator is 0.007 MPa rms on σz and 0.4% on peak, *below* the 0.0086 MPa RMSE the model itself carries against FEA. Never copy a `.pth`, a `.npz`, or the pipeline into `src/` or `public/` — `predictor.test.mjs` asserts the shipped payloads are too small to be a checkpoint.
- **Re-baking `contact-stress` is a five-stage pipeline, and stages must not share a process.** `Contact Stress Predictor/pipeline/`: `bake_fields.py` (torch) → `bake_pca.py` (numpy) → `validate_truth.py` (torch) → `validate_check.py` (numpy) → `fixture_truth.py` + `fixture_build.py` (which writes the checked-in `fixture.json`). Torch and numpy BLAS must run in **separate processes**: the conda env links two OpenMP runtimes and importing both raises OMP error #15, whose only workaround is documented as possibly producing silently wrong results. `artifact.py` is the reference decoder and `predictor.ts` must agree with it to 1e-4 MPa; the Node test asserts it. Re-run `fixture_build.py` after any re-bake or the fixture describes an artifact that no longer exists.
- **A surrogate's residuals are computed and never corrected — but as of the 2026-08 pass they are no longer a KPI strip.** `contact-stress` used to publish the vertical equilibrium closure (Σσz·A / applied load — 87% on the paper's own headline case) and the tensile fraction in an "Is the surrogate behaving?" card; that card was removed on the instructor's call, because the tool is meant to be read visually and the strip was the least visual thing on the page. `result.cmp.equilibrium` and `result.cmp.tension` are still computed in `compare()`, still drive the `cee-warn` backstop, and still pin `SAFE_RANGE` (next bullet) — so the guarantee is unchanged, it is now enforced by the slider bounds and the test rather than shown to the student. Equation 5 of the paper trains equilibrium as a *soft* penalty, so the residual remains real information; the how-to panel says so in one sentence. Same rule as the chart-value tools: record the discrepancy, never quietly correct it. **Do not re-add the card without asking** — and do not delete the residual math on the grounds that nothing renders it.
- **But a slider must not be able to reach a field that does not close, and must not reach one there is no data behind either.** A residual exists everywhere; it is not *warned about* anywhere, because the wheel-load and inflation-pressure sliders span only `SAFE_RANGE` in `equations.ts`, and that box is now the intersection of **two** constraints, not one. (1) The residual: equilibrium within ±15% and tensile fraction at or below 12%, worst-cased over every speed, rolling condition and slip the tool offers. (2) The training envelope, `TRAINED_ENVELOPE` / `trainedBox()`: **the training domain is not a box, and the manifest cannot say so** — its `domain` is the min/max columns of the checkpoint's normalization table, i.e. the *union* over the branch, and reading it as a rectangle is what let the pressure slider reach 1.0 MPa with "Braking" selected. Only free rolling at 8 km/h was simulated over the full rectangle; every other block is 18–50 kN × 0.50–0.90 MPa (braking at 8 km/h reaches down to 10 kN), and **above 0.9 MPa the FE database has not one braking or accelerating case at any load or speed**. The network answers there anyway, plausibly, with the equilibrium residual still inside the band — which is exactly why it went unnoticed. Net: **DTA 18–46 kN × 0.685–0.90 MPa** (load floor and pressure ceiling from the data, load ceiling and pressure floor from the residual), WBT 11–27 kN × 0.68–1.0 MPa, slip 0–0.99 (`SLIP_RANGE`; the FE set samples slip continuously from 1% to 99.78%, so 0–100% was never the wrong *axis* — only the load/pressure envelope that goes with it). Worst-casing across the rolling controls costs free rolling the 0.90–1.0 MPa corner, which is real data; bounds that jumped when you pressed "Braking" would read as a broken slider, so that is the trade. Three things pin the box and must all hold when it is re-derived: **every preset has to stay inside it** (a clamped preset is no longer the printed case it is named after), the DTA equilibrium floor is genuinely 0.855 at 46 kN so there is only ~0.005 of headroom, and no block of `TRAINED_ENVELOPE` may be left outside. The warning code is still in the component as a backstop. `predictor.test.mjs` re-sweeps the whole box at slider resolution and fails if a warning is reachable, and `equations.test.mjs` checks the box block by block against the envelope, so **re-baking the artifact without re-deriving `SAFE_RANGE` is caught by the test, not by a student.**
- **Nothing in `contact-stress` may scale itself to its own data — with exactly one exception, and it is not σz.** The card's subject is how load and inflation pressure change the contact stress, and every scale was originally fitted per state, so the picture held still while only the legend moved: a rib at 0.9 MPa and the same rib at 2.0 MPa came out the identical orange. Three constants hold it. `FIELD_RANGE` in `equations.ts` fixes the plan view's color scale and the vertical 3-D window's color and z axis (both, or hue and height disagree), `profileRange()` fixes the two profile cards' shared y axis, and `planFrame()` fixes the plan view's extents and therefore the canvas the card solves from them — it deliberately **takes no load and no pressure argument**, which is the guarantee. `FIELD_RANGE` is shared between the tires for σz and σy so a wide-base can be read against a dual assembly (the WBT preset invites exactly that comparison, and reaches 47% and 58% of those scales), but is **per-tire for σx**: braking and acceleration exist only on the DTA branch and are the whole of what makes σx large, so one scale would flatten every wide-base longitudinal window to 5% of it. Derive with `node --experimental-strip-types scripts/contact-stress-range.mjs --fine` (163,125 reconstructions over SAFE_RANGE × every rolling control); `predictor.test.mjs` re-runs a coarse version and fails if a reachable field runs off the scale — **Plotly clamps to the top color and says nothing**, so without that gate a re-bake would silently start lying about the peak. It also fails if a channel reaches under a third of its scale, which is the other way to get this wrong.
- **The exception is the two SHEAR windows of the 3-D card, and it was earned by measurement.** Their fixed limits are set by a hard braking case at high slip (DTA σx ±0.72 MPa) and almost nothing else came near them: on the tool's own presets a free-rolling standard axle reached **5%** of that ramp, highway speed 5%, and the Figure 8 free-rolling case the tool *opens on* 21%. At 5% the surface is a flat sheet in the neutral color — and flat in height too, because the z axis took the same limit — so two of the three windows a student first sees were blank in both encodings at once, hiding the friction traction that is the whole reason the paper models rolling condition. A scale that shows nothing is not a more honest scale. So `shearLimit(min, peak)` fits those two windows (color *and* z axis, always together) to the case. Three things keep it from becoming the original sin again: it is **only the shears** (σz, which carries 90% of the magnitude, still never moves); the limit stays **symmetric about zero** so the diverging scale's neutral stop stays on zero and neither sign is drawn louder; and it is **snapped to a round-number ladder** (`NICE_STOPS`, no gap wider than 25%) so it holds still through a slider drag and then steps once, instead of creeping every frame. The ramp bar ends print the limit and the window header prints the true min/max, because with a moving scale the numbers *are* the reading. `FIELD_RANGE`'s shear pairs stay — they still pin `profileRange()` and are still swept — so do not delete them. `predictor.test.mjs` gates both halves: the adaptive limit never clips a reachable field, and it never leaves one filling less than 80% of its own scale.
- **`contact-stress` draws on TWO schedules, and the rule is that nothing is drawn for pixels nobody can see.** A slider tick used to cost **134 ms** — React render + commit 15.8 (the physics is 3.5 of that), three gl3d surfaces 28 + 27 + 27, the plan view 9.7, the two profiles 9.8 — as ONE long task, and the footprint, the only figure anyone watches while dragging, was drawn **last**, 115 ms behind the hand. `draw` was also async and uncancellable, so a fast drag queued passes and fell further behind the longer it ran: a 2.5 s sweep delivered **18 of ~150** input events and the picture sat a steady 13% of the slider's travel behind. Now: the 2-D figures are drawn **first**; every figure is gated on visibility; a newer pass cancels an older one (`drawGen`); and the 3-D group — 82 of the 134 ms — comes off the drag onto a trailing pass, `SURFACE_SETTLE_MS` after the controls go still, with a `SURFACE_STALE_MS` escape hatch so a drag that never stops does not freeze them. Measured after: **151 of ~150 events, 60 fps, zero long tasks, 1.3% lag, and only the plan view redrawn.** **Do not try to make the surfaces cheaper instead — that was measured and it does not work**: `Plotly.restyle({z})` is *slower* than a full `react` (40 vs 33 ms) and halving the mesh saves 8 ms, because a gl3d scene costs what it costs to rebuild whatever you change. The only move is to stop rebuilding it sixty times a second.
- **Three traps in that scheduling, each of which cost a debugging round.** (1) **Two observers, not one.** `nearby` (200 px margin) decides whether a figure may be drawn at all, so one just under the fold is ready before it is scrolled to; `inView` (no margin) decides only whether the 3-D group is worth keeping alive during a drag. One observer cannot serve both — it never fires for a crossing inside its own margin — and conflating them at a 400 px margin put five full 82 ms surface passes into a 2.5 s sweep, on a card 320 px below the fold. (2) **A structural change must not wait for the settle timer.** Focusing one window resizes it 300 → 480 px and restores its axis titles; deferring that reads as a broken click, so `view|theme|unit|tire` forces the surfaces immediately. (3) **The 3-D card's numbers describe the pass that DREW it, not the live state** (`surfaced`). Its headers and its shear color bars are on a slower clock than the sliders, and a bar reading ±0.50 over a surface painted on ±0.15 is not a lagging figure, it is a mislabeled one — the shear limits move with the case, so this matters here and would not in a fixed-scale tool. Gating also means **a figure must be drawn at least once regardless of visibility**, or a card opens at zero height and the page jumps when it fills. None of this is reachable from `node --test`; it is verified in the browser.
- **`lea` is one tool with five modules, not one solver with a UI.** Huang's Chapter 2 is a ladder — Boussinesq's half-space, Burmister's two layers, Jones' three, the general N-layer solve, and the design charts that stood in for all of it — and a student is asked to move between the rungs (Problem 2.7 asks for the equivalent modulus that makes a three-layer section behave like a two-layer one). So `LeaApp.tsx` is a tab shell over `modules/*.tsx` — **"Solutions by chart" leads the strip and is the tab a first visit opens on**, because it is the rung the chapter reaches first and the only one that needs no setup: a figure is already on screen where every other module wants a section typed in first. The physics is split to match: `oneLayer.ts` (Boussinesq at any (r,z), not just the axis), `twoLayer.ts` (the five §2.2.1 design charts as computed quantities), `threeLayer.ts` (Jones' four stress factors from k₁,k₂,A,H), `lea.ts` (the N-layer core), `charts.ts` (the catalog). Each has its own `*.test.mjs` pinned to printed answers, and **they check each other**: two identical layers must give Boussinesq, two layers must give Burmister's charts, three must give Jones' table to four decimals. Those are assertions, not aspirations.
- **§2.1 is THREE problems, not one, and the One-layer module is built as a switch between them.** Huang opens the chapter saying so: Boussinesq's original is a *concentrated* load, and "the stresses, strains, and deflections due to a concentrated load can be integrated to obtain those due to a circular loaded area". So the module's first control is the load case — **point load**, **circular on a flexible plate** (a tire: uniform pressure, dished deflection, Eqs. 2.2–2.8), **circular on a rigid plate** (a plate bearing test: uniform DEFLECTION, Eqs. 2.9/2.10, Figure 2.9) — and it changes the inputs, the equations, the illustrative figure and the curves together, so the tool is never showing one case's equations over another's numbers. All three come out of one file: `oneLayer.ts`'s `Plate` type swaps a single factor of the Hankel integrand, `J1(ma)` for `sin(ma)/2`, which is the whole rigid-plate solution (∫₀ᵃ ρJ₀(mρ)/√(a²−ρ²)dρ = sin(ma)/m). Both have closed forms on the axis and at the surface, and `oneLayer.test.mjs` pins every one of them plus the limit that a small disc of the same total load IS the point load, quadratically in a/z.
- **A silent sign error lived in `surface()` and the tests could not see it.** At z = 0 outside the loaded circle it returned σr = +q(1−2ν)a²/(2r²) where the answer is NEGATIVE — the surface around a wheel is in radial TENSION and hoop compression, which is why a punch cracks a half-space radially. The quadrature disagreed at every ν, and nothing noticed, because the difference is identically zero at ν = 0.5 and that is the only Poisson ratio Foster and Ahlvin drew a chart for and the only one the suite exercised out there. `surface()` is now derived from one identity, σr = p(r) − (1−2ν)T and σt = 2νp(r) + (1−2ν)T with T = (1/r)∫P̃J₁(mr)dm, which covers both plates and cannot drift between them; the test asserts the integral converges on it as z → 0. **A closed form that only agrees with the quadrature at one ν is not tested.**
- **`oneLayer.ts` exists because Appendix B is too slow to draw a chart with.** It is the n = 1 specialization — A = C = 0, D = 1, B = 2ν — whose integrands are elementary, so there is no 6×6 solve per quadrature node: 0.03 ms a point against 0.28, which is what makes a 17-curve figure redraw in 50 ms. Its surface values are closed form (complete elliptic integrals for w, algebraic for u and the stresses) because at z = 0 the integrals lose their e^(-mz) and converge only conditionally — there is nothing for the quadrature to converge to.
- **Two defects in `lea.ts` were fixed while building on it; both were silent.** (1) Breakpoints came from a fixed cycle count applied to *both* Bessel families, so the zeros of J₁(mα) and J₀(mρ) reached different m and panels past the nearer limit straddled several oscillations. At r/a = 24, z/a = 5.6 it returned σz = −3.3e−3 where the truth is +2.9e−5 — two orders out, wrong sign — and a tandem axle at a realistic 60-in spacing samples exactly that region, so the shipped tool's own preset was affected. Both families now run to a common M, and the stopping rule counts a *run* of quiet panels against the largest contribution seen rather than against a running total that may be canceling to zero. (2) `leaSuperpose` added σr to σr regardless of direction; each load's (r,t) axes point somewhere different, so a dual mixed one wheel's radial stress with the other's tangential and dropped the in-plane shear entirely. It now rotates into a common plan frame and returns the full tensor with principal stresses, strains and critical tension. **A far-field or multi-wheel regression is invisible without a reference** — `oneLayer.test.mjs` cross-checks the two solvers out to r/a = 80 for exactly this reason.
- **`lea.ts` integrates the DIFFERENCE from a half-space of the top layer's material and adds it back in closed form.** The difference is a reflection off the first interface, so it decays like e^(−m·λ₁) even at the surface, where the response itself has no damping at all. Figure 2.17's grid went from **53 s to 194 ms** and the test suite from 11.8 s to 2.5 s. This is why `lea.ts` imports `oneLayer.ts` rather than the other way round.
- **The chart modules take no Poisson ratio, deliberately.** Foster and Ahlvin drew Figures 2.2–2.6 for ν = 0.5 so one set would serve, and Huang keeps the assumption through all of §2.2 ("As in all charts presented in this section, a Poisson ratio of 0.5 is assumed for all layers", p. 58). `CHART_NU` is baked into `twoLayer.ts` and `threeLayer.ts`; a caller who wants another ν wants `leaResponse`. Exposing it as an input would quietly stop reproducing the printed figure.
- **Figures 2.21 and 2.31 are nomographs and are drawn as nomographs — the earlier decision to rectify them was wrong.** They are lattices of two crossing families over an abscissa that carries no variable, and they were first redrawn with one family on a real axis on the reasoning that a blank axis cannot be reproduced. That threw away the figure: the *mesh* is the figure, and the abscissa is not arbitrary. Reading the plates back, **x = (the family value's position along its own family) + (the sweep value's position along its own family)**, log or linear as that family is spaced, scaled to span [0, 2] in total. Everything on both pages follows from that plus the RELATIVE gain of the two families (next bullet) — Figure 2.21's rhombic corners at (0.25, 0.25) far left, (200, 0.25) top and (200, 4) far right; Figure 2.31's H labels down the left and A labels down the right; and "A = 0.1  H = 8" printed *together* at the bottom apex, because those two curve ends land on the same x. They do here, exactly. `sampleLattice` builds the mesh, `latticeLabels` names each curve at the end the plate names it at, `latticeCorner` keeps the caption off that apex, and `nomograph: true` in `charts.ts` selects the whole path. The abscissa is still drawn blank — there is still nothing on it to read, and a tick would invite someone to read one. **Verify against the plates, never by eye**; `scripts/` has no renderer, so extract the page image from the PDF into the scratchpad (never into the repo — it is a copyrighted textbook). The instructor's handouts under `Box/CEE 406/.../Lecture 3 - Flexible Pavement Analysis/` carry Figure 2.31's six panels and Jones' Table 2.3, which is the cheapest way to check a three-layer number.
- **Two log families share ONE ruler; a mixed pair cannot — and getting that wrong bent the whole of Figure 2.31.** `latticeWeight` decides how much of the abscissa each family gets. Normalizing both to unit width, which is what it did, is only right when the two measure different kinds of thing. Figure 2.31's families are both **doubling ladders** (H over six doublings, A over five), so one doubling is one width in either and the family takes **6/11** of the abscissa, not 1/2. That 9% is measured, not argued: every one of the 39 crossings Table 2.3 tabulates for panel (a), projected onto a 300 dpi scan of the plate with the horizontal rulings masked out, lands on drawn ink — **36 of 39 for the shared ruler against 28 for half-and-half**, whose misses were the entire middle of the mesh. Figure 2.21 pairs a log family with a LINEAR sweep, which have no shared ruler, so it keeps half each and is unchanged. `invertLattice` derives its scan slice from the same weight; the two must move together.
- **Figure 2.31 is a TENSILE strain factor and is drawn only where the strain is tensile.** Table 2.3 tabulates (ZZ1 - RR1) and it goes negative over part of every k1 = 2 or 20 panel - for k1 = k2 = 2 and H = 0.125 it is +0.706 at A = 0.1 and -0.289 by A = 3.2, because a layer 1 much thinner than layer 2 under a wide load does not bend and its underside goes into compression. A log ordinate can draw neither sign everywhere, so `evaluate` stays SIGNED and `magnitude: true` makes the samplers draw `drawnValue`. **What the sign is really for is knowing where the curve STOPS.** Peattie drew no compressive part of it: `tensileSpan` clips each curve to the longest run of PRINTED STATIONS where the factor is still tension, and that is the whole shape of the printed mesh - it is why the plate has a scalloped upper-left boundary instead of running to the frame on every curve. Two earlier readings were both wrong and both shipped: returning the signed value cut curves at the zero and left eight of thirteen stopped in open space, and then `bridgeSpans` carried them ACROSS the sign change on a chord between the bracketing stations, which put a flat run and a small arch through the middle of panel (a) on ink that is not there. Measured: with the rulings masked out of a 300 dpi scan, 37 of the 39 crossings inside the frame land on drawn ink, the one real miss being H = 0.125 at A = 1.6 - the first compressive crossing - and scoring the whole polyline puts every curve within a few pixels of the plate except that curve's tail, 19 px out at p90 because nothing is under it. **The rule is certain rather than plausible because the mesh CLOSES**: every curve stopped this way ends exactly where a neighbour ends or crosses (H = 0.125 stops at (A = 0.8, 0.1116), which is precisely where A = 0.8 begins), so the stopped ends are the V-corners of the weave. `charts.test.mjs` asserts that closure on every panel.
- **A nomograph is drawn in the PLATE'S OWN BOX, and that is not cosmetic.** Its abscissa carries no variable, so nothing in the data says how wide the frame should be: the shape IS the drawing. Both printed nomographs are taller than they are wide, and put in the 1.4-to-1 box every other chart uses the same mathematically correct mesh comes out squashed flat - shallow arches, shelving legs, diamonds that read as lozenges, and a figure a student cannot lay beside the page it reproduces. `plotAspect` carries the measurement, and ChartReader pins the **container's** max-width rather than `layout.width`, because `plotConfig` is `responsive` and would overwrite a layout width on the next resize. **Measure frame-line CENTRES, and measure the height as carefully as the width.** 2.31 shipped at 1068/1401 = 0.762 for a year; re-measured on a 300 dpi render its frame is 535 x 733.5 = 0.729, and the height was the half that was wrong - the width agreed to two pixels. Four percent is visible on a nomograph. The method is sound rather than merely new: Figure 2.21 measured the same way comes out 756 x 868 = 0.871 against its shipped 0.873, and 2.31's frame at 733.5 px is what makes 37 of 39 printed crossings land on ink. Drawn aspect now 0.730 against the plate's 0.729. Also: **`LATTICE_RANGE` is exactly [0, 2]**, so the mesh fills its frame the way the plate's does; the two corner labels push inward instead of sitting outside the box.
- **How a chart is checked against its plate, now that there is a method.** Render the page to 300 dpi with `pymupdf`, mask the horizontal rulings out by run length so only curve ink is left, find the frame line to line, and project. Two scores, both worth having: every crossing the table prints (Figure 2.31 lands 36 of 39 within 8 px), and the whole drawn polyline (97.9% within 1.3% of the frame width, 99.2% within 1.9%). The first found the abscissa weighting; the second found nothing, which is how the aspect ratio survived — a shape error moves every point a little and scores well on both. **Look at the two side by side at matched height before believing either number.** Do the work in the scratchpad; the plates are copyrighted.
- **A lattice curve ends at a frame edge, at the end of its own parameter range, or - on a magnitude chart - on another curve of the mesh, and nowhere else.** That is the whole of what "closed mesh" means, and `charts.test.mjs` asserts it over every curve of every panel of both nomographs. The third case is the tensile stop above, and asserting that such an end lands on a neighbour is what stops the truncation from ever degenerating into loose ends. It has failed three ways over time: curves cut at a sign change, curves carried across one on a chord that is not on the page, and curves whose run-out to the border gave up short - `edgeApproach` stopped bisecting at twice the axis floor, a third of a decade, which on Figure 2.31's five-decade frame is 19 px of daylight between the curve and the border it should cross. Its log target is now just BELOW the floor, inside the 10% grace `frameTest` keeps, so Plotly clips the segment at the frame line.
- **Where the book's printed answer and the computed one disagree, the test records both.** Problem 2.1 (r = a, z = 2a): Huang prints σ = 0.221q, 0.011q, 0.004q and w = 0.58qa/E from Ahlvin and Ulery's tables; two independent solvers here agree on 0.22805, 0.01082, 0.00919 and 0.57207. Same rule as the other chart-value tools — record the discrepancy, never quietly correct it.
- **A lattice still inverts, and three of its roots are invisible to a sign-change scan.** x fixes one combination of the two parameters and the ordinate fixes another, so a point in the mesh solves to a (family, sweep) pair — a question the printed page cannot answer at all. `invertLattice` scans the slice of the family that can reach that abscissa, and it has to handle three cases that a plain sign test walks past, **all of which are printed crossings, i.e. exactly the points a student types**: a root on the END of the reachable slice (the whole left and bottom edge of the mesh — E₁/E₂ = 1 at h₁/a = 4 is one), a root at a CORNER where the slice is a single point, and a TANGENCY, where the response turns over exactly at a crossing so the residual touches zero and retreats without changing sign (E₁/E₂ = 0.5 at h₁/a = 3 reaches −8e−7 and comes back). The first returned "no such section"; the second, nothing; the third, the wrong pair. All three are pinned by `charts.test.mjs`, which probes every crossing of both plates.
- **A curve on one of these plates ends at a label or off the edge of the frame — never in open space.** A *sampled* curve ends wherever the last sample that happened to be inside the frame was, which is fine until the samples are coarse or the function is steep. On Figure 2.31 both fail at once: the strain factor changes sign in one corner, so on a log ordinate it plunges two decades inside one sample interval, and the chart is expensive enough to be sampled 22 times. Eight of its thirteen curves ended in mid-air, four of them one to two decades short of the floor they should have run off. `edgeApproach` bisects for the frame crossing wherever two samples straddle it and splices in the crossing plus three interior points — the interior ones matter, or a two-decade dive is drawn as a chord, a straight cliff where the function has a curve. Both samplers use it, so every chart closes. `latticeLabels` then names a curve at the outermost point that is actually ON the page rather than the outermost DRAWN point: the samplers keep 10% of grace outside the ordinate so a curve crosses the frame line instead of stopping on it, and a number placed out there is clipped away — which is how Figure 2.31's H = 4, H = 8, A = 0.2 and A = 0.1 came to be drawn and left unnamed while the plate names all four.
- **Figures 2.23 and 2.25–2.27 are four figures, and each one is a PAIR.** They used to be a single catalog entry with eight panels in a select, which made a reader switch panels to apply an equation that needs both at once: Eq. 2.19 is C = C₁ + 0.2(a′−3)(C₂−C₁), so C₁ (a = 3 in) and C₂ (a = 8 in) are read together. `stack` on a ChartSpec is that — two panels drawn one over the other, sharing every input, both markers moving together, both values in the readout — as against `panel`, which is a chart you choose between. A spec has one or the other, never both. The four differ only in tandem spacing and are built from one factory, so anything true of all four is true by construction.
- **Figure 2.15\* is ours, not Huang's, and is labeled so.** The printed Figure 2.15 draws interface stress on the axis only, one curve per modulus ratio. The variant fixes E₁/E₂ = 100 and makes r/a the family, which is the question a dual wheel asks — how far sideways the stress at the top of the subgrade reaches. It keeps **both of the parent's axes unchanged** so the two can be read against each other, and the cost is that its family never leaves the bottom third of the ordinate; shrinking the axis to fit would throw away the comparison that is the whole point. Its r/a = 0 curve must equal the parent's E₁/E₂ = 100 curve, and `charts.test.mjs` asserts it.
- **A chart whose abscissa is a percentage of q owes the reader both steps.** Figures 2.2–2.5 print σ/q × 100, so a read is divide by 100, then multiply by the contact pressure — and the factor of 100 is set in small type beside the axis and is the most-missed thing on the page. `percent` on a ChartSpec names the ratio and the stress, and the reader shows the whole ladder under the value (Example 2.1: 28.4 → σz/q = 0.2845 → 14.22 psi at q = 50). The test asserts exactly the charts whose equation divides by 100 declare it, and no others.
- **`charts.ts` is a catalog, and `invertFamily` is the half a printed page cannot do.** Given a point on the chart it solves for the curve through it, returning *every* root (σt and τrz hook back, so two radii can give one stress) and *none* when the point is off every curve. It scans for sign changes and bisects — and it must treat an exact zero as a root, because the family values are round numbers and the scan is a round division, so they coincide constantly: r/a = 2.5 on a 240-step scan of [0,12] is step 50 exactly, and a strict `prevF * fv < 0` walked straight past the chart's own labeled curve.
- **Three charts must not be recomputed on hover, and `heavy` is what says so.** Every point of Figures 2.23/2.25–2.27 is a critical-strain search over a whole wheel group (~37 ms), so `nearestCurve` takes the curves *already drawn* rather than re-sampling, and the inverse is gated behind a click on `heavy` charts. Re-sampling on mousemove would be seconds of work per frame to answer a question about where the mouse is. **Figures 2.21 and 2.31 joined that set when they became lattices**: a mesh is both families, nineteen curves rather than eight, and 2.21's evaluator is itself a critical-strain search — the figure went to 3.4 s to build and 1 s to invert. They are `samples: 22` and `heavy: true`, which brings that to 0.9 s and 0.7 s, behind the loader and behind a click. Do not raise their sample count without re-measuring.
- **Eighty per cent of the chart module's running time was one 6×6 linear solve, and it was allocation, not arithmetic.** `constantsFor` in `lea.ts` is called once per Gauss node of every panel of every Hankel integral — a few hundred thousand times for one point of a heavy chart — and it was building a fresh `n×n` matrix of JS arrays, a fresh augmented copy, an object per coefficient write and a closure per index lookup, every time. Profiled, that block plus its garbage was **77%** of "Solutions by chart". It is now assembled in place in a reused `Float64Array` and solved by LU with partial pivoting and back substitution instead of a Gauss–Jordan sweep that eliminated above the diagonal only to divide the result out again; `starred`/`starredHalfSpace` write into caller-owned buffers rather than returning an object apiece, the two `J0(mρ)`/`J1(mρ)` calls they duplicated are computed once, Eq. B.12's `R_i` is hoisted out of the node loop, and the panel breakpoints are cached on (α, ρ, M) the way `oneLayer.ts` already cached its own. **Result: 3.5× to 9× across every chart** — Figure 2.19 1554 → 284 ms, 2.21 1780 → 198, 2.31 1825 → 411, 2.23 8.9 s → 1.1, 2.27 57 s → 14. The buffers are module-level and therefore **not reentrant**, which is safe only because the single caller consumes each result before asking for the next; do not export `constantsFor`. Verified, not assumed: a sweep of the whole domain the charts draw — two- and three-layer sections, r/a to 60, and the superposed dual-tandem groups — agrees with the previous implementation to **3.3e-13** relative.
- **Coarsening the quadrature panels was tried, measured and thrown away — do not re-propose it.** Off the axis the zeros of J₀(mρ) and J₁(mρ) interlace, so the union gives panels a QUARTER of an oscillation wide where 8-point Gauss–Legendre carries a half comfortably, and merging them under a phase cap halves the panel count for the far wheels of a tandem group. It bought **15%** — because the per-node cost is the linear solve, not the node count — and moved the response by up to **6e-8** relative. That is a real change to a quadrature that had just been repaired for exactly the far-field case it touches (a tandem at a realistic spacing samples ρ ≈ 36, where the layered and half-space integrands cancel to four orders below their own size). Fifteen percent is not worth spending that. The note in `panels()` records it. **The remaining lever, if one is ever wanted, is batching by radius**: `constantsFor` depends only on m and the materials, never on ρ or λ, so one shared m-grid across the sixty radii a `criticalTension` call evaluates would compute it once instead of sixty times — modelled at ~2.6×, at the cost of a batched API through `leaSuperpose` and a grid change for every near point.
- **`charts.ts` memoizes `evaluate` on the heavy charts, and the table is the reason.** The reader asks for the same points from five places that know nothing about each other: the sampler walks the curve, `tensileSpan` walks the printed stations first, the table under the figure reads every curve at every printed station, the checkpoints re-evaluate the book's own reads, and switching panels and coming back redraws a chart already drawn. On Figure 2.27 the table alone was 80 critical-strain searches — **seven seconds, inside the React render pass**, before the browser could paint the card, and again on every keystroke. Every one of those 80 points is already a drawn vertex, so `chartValue` answers all of them free; `charts.test.mjs` asserts the table costs **zero** fresh solves. The key rounds to twelve significant figures because the sampler reaches a station through a parameter round trip that does not always land on the same double, and a cache the table misses by one ulp does nothing for the slowest chart in the tool. Only `heavy` charts are cached — elsewhere `evaluate` is 10–25 µs and the key would cost a measurable fraction of it — and the INVERSE deliberately does not use it: a 240-step scan lands on 240 parameters nothing will ask for again, and on a light chart it runs per pointer move. A side effect worth knowing: revisiting Figure 2.27 is **173 ms** against 25 s cold.
- **The chart samplers are generators, and `ChartReader` drives them against a clock.** `sampleCurveGen`/`sampleLatticeGen` yield after every vertex; `sampleCurve`/`sampleLattice` are thin drivers that run them to completion, so tests and every other caller are unchanged. The reader yields to the browser whenever a slice has held the thread 24 ms, publishes each curve as it lands, and shows a determinate progress bar over the top — `ProgressStrip`, `docs/loaders.md` §7.6, the first loading state in the repo. Three things were measured rather than guessed. **Handing the thread back is nearly free**: 208 yields cost 840 ms against 24.5 s of arithmetic, 3.3%. **`scheduler.yield()` is the wrong primitive here** — it resumes its continuation ahead of other pending tasks, which starved the progress bar's own interval so the elapsed clock never advanced and the strip, which will not appear before its entry delay, never appeared at all; a plain MessageChannel post goes to the back of the queue, where a long build belongs. **The channel is built on first use, never at import**, because a MessagePort with a listener holds Node's event loop open and `render.test.mjs` server-renders this island. Curve labels and the caption wait for the last curve: they are a judgement about the whole drawing, and solved against three of sixteen curves they walk across the chart as it fills.
- **Nothing on the pointer path may redraw the figure, and `Plotly.restyle` is not an escape hatch.** Hovering used to rebuild the whole figure every frame — seventeen traces, the contour-label solve, a full `Plotly.react` — to move one cross a few pixels: 83 ms a move on Figure 2.27 and a long task for every one. Moving the mark to its own trace and restyling only that did **not** fix it: `Plotly.restyle` is a full replot internally, **43 ms a call** on this figure, 86 ms across two panels. The hover mark is therefore gone, not cheaper — it was drawn exactly where the cursor already was, so the cursor says the same thing for free — and only a PINNED reading gets a mark, which a click can afford. The inverse is deferred too: heavy charts wait for a click as they always did, light ones for the pointer to hold still (`SETTLE_MS`), because a 240-step scan is 30 ms even where `evaluate` is cheap. Pointer cost now: **22 ms a move on Figure 2.2, 33 ms on Figure 2.27 with zero long tasks.**

It bundles the TSX with esbuild and server-renders every module and all twelve chart configurations; effects never run, so no Plotly and no canvas are needed. It pins what only holds if someone checks: ramps reverse by mode so the HIGH end is always the one standing off the card; the diverging scale's midpoint *is* the surface token, its arms are within 1.15× in contrast so neither sign looks louder, and its ends survive simulated deuteranopia/protanopia. Dark mode is comfortable (5.5–10.2:1); **light mode is the tight side** — the hues run 2.65–4.23:1 on white, under WCAG 1.4.11's 3:1, tolerated because Illini Orange is itself 2.96:1 and `<Legend>` always pairs a swatch with AA text so hue is redundant coding. `light.amber` is the one real failure at **1.81:1** and is pinned in its own test with the reason it was not silently patched (3:1 turns it olive, and darkening it toward orange collides with the brand); its consumers — aashto, esal, reliability — are all release-locked, so nothing ships it today.
- **`rampSeries` for an ORDERED family of lines, never the categorical six.** Huang's seventeen r/a curves are one quantity at successive parameter values; the §B4 hues say "different things" and would throw the ordering away. It works from the four ramp stops that survive on each surface — the pale 100 is 1.11:1 on white and the deep 900 is 1.68:1 on the navy card, fine for a heatmap cell that has area and invisible as a 2 px stroke — and light mode extends past 900 toward the ink to keep the span wide. Light is the tight side at 2.14:1, tolerated for the same reason §B4 tolerates it: curves are direct-labeled and every chart keeps its table view. Gated in `chartTheme.test.mjs`.
- **`withAlpha` for flat marks, `mixHex` for 3-D ones.** Alpha means "let the background through", which is right for a 2-D `fillcolor` or `areaFill`. In a colorscale on a gl3d `surface` it is applied to the *mesh*: a translucent stop makes the sheet see-through, the far side and axis walls bleed through the near side, and Plotly's depth sort picks a winner per viewing angle. `contact-stress` shipped `withAlpha(hue, 0.45)` at its diverging quarter-stops and had exactly that. `mixHex(fg, TOKENS[theme].surface, t)` gives the intended fade and stays mode-correct because it fades into the card it is drawn on; the gate asserts no colorscale stop is anything but opaque hex.
- Always build internal links with `import.meta.env.BASE_URL`.
- Theme key is `localStorage('cee406-theme')`; `[data-theme="dark"]` overrides live in `global.css`.
- KaTeX auto-renders `$...$` inside elements when the page has `.doc-equation` or `[data-katex]`.
- Signature visual: pavement cross-section motif — `PavementHero.astro` (canvas: tandem axle bogie, superposed pressure bulbs, viscoelastic deflection basin), `LayerGlyph.astro` (per-HW glyph), footer layer-rule. Keep new UI consistent with it.
- **Math inside an island is `ui/Equation.tsx`, not the page's KaTeX auto-render.** The site loads KaTeX on every page, but the auto-renderer runs once at DOMContentLoaded over elements that exist then, and a `client:only` island does not; it also scans for `$…$` in text React would overwrite on the next render. `Equation` polls for `window.katex` and calls `katex.render` on a span React is given no children for, with a plain-text fallback that doubles as the accessible name. Two traps: `throwOnError: false` does NOT throw — it renders the source in red and returns normally, so success is detected by looking for `.katex-error`; and **TeX in a TypeScript string literal needs its backslashes doubled**, or `\frac` becomes a form feed and `\sigma` becomes the letters "sigma". Nothing catches that — not the build, not `renderToString` — so `render.test.mjs` reads the source and asserts every run of backslashes inside a `tex:` literal is even. Nine equations shipped broken before it existed.
- Tool UX standard: every input gets a `Tip` tooltip, every tool gets a `<details class="cee-howto">` how-to panel and `cee-warn` validation messages. Don't use CSS `text-transform: uppercase` on labels containing Greek letters (σ → Σ); write labels pre-uppercased.
- **Dependency pins**: `astro@6.0.8` and `@tailwindcss/vite`/`tailwindcss@4.2.2` are exact pins — `@tailwindcss/vite` 4.3.x pulls Vite 8 against Astro's Vite 7 and the build fails ("Missing field tsconfigPaths"). Don't bump without testing.
- Plain CSS files don't support `:global()` — in `global.css` write `[data-theme="dark"] .foo` directly.

## Content policy (IMPORTANT — the repo is PUBLIC)

**The repository and its Pages site are public.** Anything committed is world-readable at `github.com/ictuillinois/CEE-406` and at `raw.githubusercontent.com`, whether or not a page links to it, and whether or not it is later deleted — git keeps history. Assume every file you add is published the moment it is pushed.

- `Chapters/` and `Homeworks Fall 2024/` at the repo root are **gitignored Box source archives** and hold the instructor's originals, solution keys included. They are the restore source; nothing below deletes them.
- **The textbook is not ours to distribute.** Huang, *Pavement Analysis and Design* (2004) is a copyrighted commercial text. All 20 chapter/appendix PDFs were removed from `public/textbook/` and **purged from git history**; `public/textbook/` is gitignored so they cannot be re-added by accident. The chapter pages survive as a reading map — citation, the course's own chapter summaries, related homeworks — and link to the [UIUC Library record](https://i-share-uiu.primo.exlibrisgroup.com/nde/fulldisplay?docid=alma99598836912205899&vid=01CARLI_UIU:CARLI_UIU_NDE). `TextbookEntry` deliberately has no `pdf` field.
- **Never publish**: solution keys (`*Key*`, `*solutions*`), graded student submissions (e.g. `Lara Diab`), exams (`Final Exam*`), or third-party publications you have not confirmed you may redistribute — AASHTO standards, textbook excerpts, and reproduced chart/table handouts are the ones this course has previously carried.
- **Publishing is opt-in, per item, via `src/data/release.ts`.** Nothing is visible until it is released there. Hiding a card is not enough — see below.

## The release gate (`src/data/release.ts`)

One file, edited weekly, is the single source of truth for what the site shows. "Hidden" has **three** independent meanings and all three are enforced by `src/data/release.test.mjs`:

1. **No card** on any index — `homeworkLock()` / `toolLock()`, used by the landing page, both indexes, and the chapter pages.
2. **No route** at the URL. A homework page is generated from data, so `getStaticPaths` filters to released ids. A tool page is a *file*, so hiding its card does nothing: the locked ones are renamed `_index.astro`, which Astro does not route. **Releasing a tool is therefore two steps** — add the slug to `RELEASED_TOOLS` *and* rename `_index.astro` → `index.astro`. The test fails if the two disagree in either direction.
3. **No file** under `public/`. A PDF in `public/` is served whether or not anything links to it. `public/homeworks/` is empty; unlocking a homework means copying that week's files out of the Box archive into `public/homeworks/<id>/`. The test fails if files exist for an unreleased homework.

**A tab-shell tool gates its modules too, and that is the ONE case with only one meaning of hidden.** `RELEASED_TOOL_MODULES` / `moduleLock(slug, id)` dim a module's tab and make it inert; a tool with no entry has every module open, so this costs the other twenty nothing. A module is not a route and not a file, so **its code ships in the island's bundle whether or not the tab is shown** — deliberate, and the limit of what this can do. These are solvers for equations printed in a textbook in a public repo, so a dimmed tab is sequencing, not concealment; never gate anything here that would matter if it were read. The shell must open on a released module (a stale `localStorage` id is re-checked against the gate, not just against the module list) and a locked tab gets `aria-disabled` + `tabIndex={-1}` + no click handler — `renderToString` can see the first two but never the third, so the click path is held by construction and pinned in the browser, not in CI.

Currently released: **tools** `gear3d`, `cross-section-studio`, `contact-stress`, `lea`; **modules** `lea` opens on `charts` and `one`, its three layered solvers waiting for HW3/HW4; **homeworks** none. Locked items render as a dimmed, dashed, non-interactive card with a lock chip reading "Coming soon", or "Releases week N" once `HOMEWORK_WEEK` / `TOOL_WEEK` carry the real semester calendar.

## Deployment

- Push to `main` → `.github/workflows/deploy.yml` → GitHub Pages. **Current state: enabled, private, `build_type=workflow`, live at `https://glowing-pancake-8gkkgl1.pages.github.io/`** (first successful deploy: run #3, 2026-07-13).
- The workflow auto-detects Pages visibility (`gh api .../pages --jq '.public'`) and sets `PAGES_PUBLIC` for the build:
  - private (current): `base: '/'`
  - public: `base: '/CEE-406/'`, site `https://ictuillinois.github.io`
- `actions/configure-pages` **cannot enable** Pages with the workflow token here (runs #1–2 failed on it); Pages was created via the REST API with a user token. The step is harmless now that Pages exists.
- On this dev machine `gh` is not installed. For REST API calls, get a working token with
  `git -c credential.useHttpPath=true credential fill` fed `protocol=https / host=github.com / path=ictuillinois/CEE-406.git` — the returned `gho_` password works as `Authorization: Bearer`. (Plain host-only `credential fill` returns stale PATs that 401.)
- Before changing anything deployment-related, check current visibility:
  `GET /repos/ictuillinois/CEE-406/pages` → `{public, html_url}`
- **Pages source must be "GitHub Actions", not "Deploy from a branch".** If it is set to a
  branch, GitHub additionally runs its built-in `pages build and deployment` (Jekyll) workflow
  on every push, which fails on an Astro source tree — a red run per commit even while
  `deploy.yml` succeeds. The two are different workflows; check the *name* in the failure
  notification before debugging `deploy.yml`. Fix in Settings → Pages → Build and deployment →
  Source: **GitHub Actions**, or `PUT /repos/ictuillinois/CEE-406/pages` with
  `{"build_type":"workflow"}`.
- `.nojekyll` exists at the repo root and in `public/` (so it lands in `dist/`). Both are
  required: the root one neutralizes the legacy Jekyll builder if the source is ever a branch,
  and the `public/` one keeps Jekyll from stripping Astro's `_astro/` directory out of the
  published artifact — directories beginning with `_` are dropped by Jekyll.
- On this dev machine the credential helper is Git Credential Manager, which only prompts via
  GUI. `git credential fill` therefore hangs or returns nothing in a non-interactive shell, and
  the repo is private so the REST API 404s unauthenticated. To inspect a failing run, either
  read it in the browser or run the API call yourself with a PAT.

## Per-student datasets (`scripts/`)

- `scripts/datasets.mjs` generates one student's whole-semester data deterministically from
  `hash(UIN + salt)`; `scripts/generate-datasets.mjs` is the instructor CLI that writes per-student
  CSV bundles plus `_answer-key.json`. Nine handouts cover HW1–HW10: triaxial M_r, CBR, W-4 table,
  drainage site, IDOT scenario, rigid slab, axle distribution, FWD survey, and the scalar assignments.
- **Draw order is the RNG contract.** Inserting a new generator anywhere but the end of
  `studentBundle` silently reshuffles every dataset drawn after it. Append new generators last and
  sort them into homework order in the returned object, which does not affect the stream.
- **The salt is the whole security model.** This repo is readable by the class, so an unsalted run
  produces data whose answers any student can re-derive from the source. The CLI refuses to run
  without `--salt`. Keep it out of git and change it every semester.
- Never publish `_answer-key.json`, and never add truth values (k₁–k₃, true CBR, station moduli,
  the section-break location) to a student-facing file. `scripts/datasets.test.mjs` enforces this,
  and the tests also assert every generated dataset is *solvable* — the Mr data regresses back to
  its own k-values, the CBR curve reduces to its own CBR, the FWD basins backcalculate to the
  moduli that made them, every slab lands where the thickness decision is real (σ/MR between 0.2
  and 1.35), and the drainage layer carries its own inflow.
- Some datasets are tuned for **pedagogical distribution**, not just validity, and the tests pin
  those distributions: roughly half the class gets a filter gradation that fails at least one
  criterion (or HW6 P5's "propose a fix" is vacuous), both fatigue and erosion govern for somebody
  in HW9 P4, and HW2's injected outliers never land on the first or last readings. Changing a range
  without re-checking these will quietly hollow out an assignment.
- Rationale and the homework redesign that depends on it: `docs/HW_Recommendations.html`.
